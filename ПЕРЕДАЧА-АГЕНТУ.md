## 3. Ключевые настройки (обязательно к применению)

### 3.1 Токен деплоя

Секрет GitHub: **`VK_DEPLOY_TOKEN`**.

Где лежит значение на компьютере Максима:
```
C:\Users\kozel\.config\configstore\@vkontakte\vk-miniapps-deploy.json  →  поле access_token
```
Длина 220 символов, начинается с `vk1.a.`.

На ноутбуке этот файл будет другим. Скрипт для копирования токена в буфер обмена:
`Скопировать-токен.cmd` (лежит рядом с этим документом, поправить путь к json внутри).
На ноутбуке проще сделать свой деплой локально и положить токен оттуда.

### 3.2 ГРАБЛЯ №1: токен отзывается

Каждый **локальный** запуск `npm run deploy` выпускает новый токен и **отзывает старый**
(в OAuth-ссылке есть `revoke=1`).

Следствие: если сделать локальный деплой, секрет в GitHub станет нерабочим, и все CI-деплои
упадут с `invalid access_token`.

**Правило: локальный `npm run deploy` больше не запускаем. Деплоит CI.**

Если всё-таки запустили локально: обновить секрет `VK_DEPLOY_TOKEN` свежим значением.

### 3.3 ГРАБЛЯ №2: токен не вставляют текстом команды

Один раз в секрет попал не токен, а текст команды (`(Get-Content ...`), 138 символов вместо 220.
Ошибка была `invalid access_token`.
В CI теперь стоит шаг проверки длины секрета — если длина не 220, сразу видно.
При обновлении секрета вставлять **только значение**, не команду.

### 3.4 ГРАБЛЯ №3: в CI обязательна сборка

`npx vk-miniapps-deploy` не вызывает `predeploy`. Без явного `npm run build` падает с
`File ./dist/index.html not found`. В воркфлоу шаг сборки есть, не удалять.

### 3.5 ГРАБЛЯ №4: временная ошибка VK

`Error: 15: Access denied: invalid file` — транзиентная. В воркфлоу 3 попытки с паузой 30 сек.

### 3.6 ГРАБЛЯ №5: подтверждение деплоя

Прод-деплой VK подтверждает кодом. CLI с этим конфликтует в CI (виснет на stdin).
Решено: `npx vk-miniapps-deploy < /dev/null` + `timeout-minutes: 15` на job.

### 3.7 Секреты фронтенда (когда появится Supabase)

`VITE_*` вшиваются в бандл **на этапе сборки**. Значит:
- прод-ключи лежат в GitHub Secrets и подставляются в шаге `npm run build` в CI
- в репозитории только `.env.example` с пустыми значениями
- `.env` в `.gitignore`
- `service_role` ключ в клиент и в гит **никогда**

**Это ещё не сделано** — пункт в задачах ниже.

## 4. Как работаем (процесс)

```
своя ветка от dev  →  PR в dev  →  тестовая версия в VK
                  →  PR в main →  боевая версия в VK (автодеплой)
```

1. `git checkout -b feat/что-делаю` (от `dev`)
2. правки, обязательно `npm run check` (это `vite build`)
3. `git add . && git commit -m "..." && git push -u origin feat/что-делаю`
4. PR открываем в **`dev`**, не в `main` (в `main` уезжает сразу в прод)
5. `main` защищён: напрямую не пушится, только PR, одобрение не требуется

Запуск локально: Windows — двойной клик по `start.cmd`; Mac/Linux — `./start.sh`.
Порт **3000** (не 5173).

## 6. Текущие задачи (по приоритету)

### 6.1 Разобрать авторизацию — блокирует всё остальное
`zertaaa` сделал `src/Profile.js` (модуль профилей на Supabase) и в нём использует
**Supabase auth** (`supabase.auth.getUser()`, `id = user.id`).
А в нашей схеме `registrations` привязана к **VK ID** (`vk_user_id`).

Нужно выбрать одно:
- **вариант А**: Supabase + вход через VK (профиль по `auth.uid()`) — рекомендую
- **вариант Б**: без Supabase auth, хранить `vk_user_id` от VK-моста

И привести `supabase/schema.sql` к единому стилю: сейчас политики сравнивают
`vk_user_id = auth.jwt()->>'sub'`, это работает только если туда класть uid из Supabase.

### 6.2 Две базы Supabase
`zetra` предлагает две: общая dev для команды + отдельная prod. Согласовано — делаем так.
Нужно:
- создать оба проекта в Supabase
- `.env.example` в репозиторий, реальные ключи локально
- прод-ключи в GitHub Secrets (`VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`)
- в `deploy.yml` передать их в шаг сборки
- `supabase/schema.sql` накатить на обе базы (один источник правды)

### 6.3 Открытый PR #1 (от `zertaaa`)
https://github.com/zerk235/chipsony/pull/1 — файл `src/Profile.js` (+122 строки).
Файл нигде не импортирован, сборку не ломает, но:

1. `@supabase/supabase-js` **нет в `package.json`** — как только файл подключат, сборка упадёт
2. Нужен `.env` с `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY`
3. Не соответствует схеме (см. 6.1) и таблицы `profiles` в ней нет
4. PR открыт в `main`, а не в `dev` — просить переоткрыть в `dev`
5. Заготовка таблицы, которую просим добавить:

```sql
create table if not exists public.profiles (
  id uuid primary key references auth.users(id) on delete cascade,
  display_name text not null default 'Гость',
  avatar_url text,
  phone text,
  city text,
  updated_at timestamptz not null default now()
);

alter table public.profiles enable row level security;

create policy profiles_read_own on public.profiles
  for select using (id = auth.uid());
create policy profiles_update_own on public.profiles
  for update using (id = auth.uid());
```

## 8. Чего делать нельзя

- Локально не запускать `npm run deploy` — отзовёт токен в CI (см. 3.2)
- Не коммитить `.env`, ключи, токены
- Не пушить в `main` напрямую — GitHub отклонит
- Не коммитить `dist/` (в `.gitignore`)
- Не удалять шаг `npm run build` и `concurrency` в воркфлоу
- Не открывать PR сразу в `main`
- Не выкидывать текст команд в PowerShell целиком вместе с пояснениями — только сами команды
